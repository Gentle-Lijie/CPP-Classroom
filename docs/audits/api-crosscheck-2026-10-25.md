## 必须单列的中间补丁安全风险

**X01 / P1 / A01 确认，非原平台问题。** `classroom.ts:259 addMember` 用全局用户名 `student.${number}` 查找已有账号，任何教师可把这个账号直接加进自己的课堂；`:325 resetPasswords` 随后仅检查该账号是本课堂 active 学生，就修改全局密码、删除全局会话、停止其所有课堂任务。组合足以接管其他教师学生账号，无需原密码或原教师授权。无需真实重置即可从授权与 SQL 路径证明。应先隔离未验收的新增重置 API/UI，之后再设计重置授权边界；本审查未实施隔离，已通知 root。

## 新发现的遗漏

### X02 / P2 / 关闭和重排未参与练习版本锁，旧编辑可覆盖新状态或顺序

`classroom.ts:488 updateExercise` 以 version 乐观锁更新状态、position；`:523 closeExercise` 仅修改 status，不增加 version/updated_at；`:450 reorder` 修改 position 也不增加 version。教师先打开编辑页，再从其他窗口关闭该题，旧编辑仍携带原 version 与“已发布”状态，提交可直接重新发布；重排后保存旧编辑也可把 position 写回旧值。不是理论上的任意 DB 修改，都是现有公开 API 的合法交错。需让所有同实体写入统一参与版本控制，或按字段更新避免旧值覆盖。

### X03 / P2 / 禁止重交校验存在并发穿透

`teaching.ts:69 submit` 先 SELECT 是否已提交，再独立 INSERT；schema 无阻止重复的唯一键或事务锁。两个首提请求都能在 INSERT 前看到无记录，allowResubmit=false 时仍插入两条。S11 的重复点击不仅是按钮反馈问题，还能绕过服务端禁止重交策略。需在数据库事务中串行化同用户同题的允许判断；不能简单对所有提交加唯一键，因为允许重交时本就需要多份历史。

### X04 / P2 / 关闭运行策略与入队之间有竞态

`runs.ts:create` 在事务外读取课堂/练习可写及 allowRun，之后才锁用户/队列并 INSERT；classroom.update 停止当时已有 runs，既不共享入队锁，worker 也不复查课堂/练习状态。若关闭课堂/关闭运行发生在权限读取后、INSERT 前，更新扫描不到新任务，随后仍可入队执行。移除成员/停用账号与入队亦有相同校验时序，但是否命中取决于实际并发，不声称已环境复现。应把最终 admission 与权限撤销置于一致锁/事务协议。

## 不应作为确定 P1 或独立缺陷统计

- A12 满员仍收 pending 申请、A14/T33 下调人数限制、T10 关闭是否强停：需明确候补/仅限制新增/运行终止政策。API 状态本身不证明这些政策错误。
- T23 ZIP 导出、T22 题目筛选、T37 搜索/拖拽、S20 请求合并是产品增强或性能风险；没有负载证据时不能报已发生性能故障。
- T26 导出不是一致性快照，技术事实成立；若定位是便捷作品导出，而非数据库备份，则严重度需按实际一致性承诺判断。
- A05 个人改密 UI 缺口成立；API 当前已对所有登录角色开放，不能描述为后端没有改密能力。
- S11 多次提交/求助不自动等同数据损坏：允许重交时多历史可合法；禁止重交时并发穿透另见 X03。求助新增/更新不一致另归 S17。
- schema 的 classroom_id/exercise_id 独立外键不是跨课堂越权实证：当前公开写入口先校验 exercise 属于课堂，runs/workspace/projection 查询也绑定 classroom_id。未发现仅猜 UUID 即可跨教师读取其他课堂草稿/运行/投屏的直接路径。
- 管理员被 classroom.access 排除是当前显式角色规则；没有管理员必须查看所有学生代码的需求证据，不报“管理员权限不足”。
- S01–S09 等前端异步问题不因 API 可读而被否定；本交叉审查未做浏览器时序验证，保留其静态证据等级。视觉尺寸/滚动项仍属待验，不纳入 API 缺陷数。
